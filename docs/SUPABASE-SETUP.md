# Supabase setup

1. Create or choose your Supabase project. Keep production and test data separate. Install the Supabase CLI and Docker for full local integration checks; sign in and link the project.
2. Apply supabase/migrations in filename order (202610040001_private_data.sql adds each user's preferences, journal key locked by the recovery code, Flee records, encrypted journal entries and confessions, and reading position, all owner-only) with `supabase db push`, or paste each migration in the dashboard SQL editor. They create profiles, links, sharing settings, shared events (no text), short messages, subscriptions and reminder preferences. RLS is enabled throughout. Direct link mutation is denied; RPCs enforce same sex and the eight-brethren cap with a transaction lock. Pending request and code lookup RPCs return only the necessary name/church details. Code lookup is capped at 20 attempts per user per hour.
3. In Authentication > Providers enable Email. Configure a production SMTP service and rate limits (Supabase's built-in email sender allows only a few emails an hour). Set Authentication > URL Configuration > Site URL to the deployed Mortify HTTPS URL. Everyone signs in during onboarding by typing a code from the email, because an installed iPhone web app cannot receive a tapped link. In Authentication > Email Templates, edit **Magic Link** (and **Confirm signup**) so the email shows the code, for example `Your Mortify code is {{ .Token }}`. Without `{{ .Token }}` users receive only a link and cannot finish signing in from the installed app.
4. Copy the project URL and publishable/anon key into .env.local using .env.example. These are client configuration; NEVER put service-role keys, VAPID private keys or Firebase private credentials in VITE_ variables. Add the same public values to Vercel and rebuild.
5. Generate a VAPID key pair with web-push (for example `npx web-push generate-vapid-keys`). Add the public key to VITE_VAPID_PUBLIC_KEY. In Edge Function secrets add VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY and VAPID_SUBJECT (a mailto support address). Use your real support contact.
6. Generate separate random MESSAGE_WEBHOOK_SECRET and REMINDER_SECRET values; store them as function secrets. Deploy `supabase functions deploy push-message` and `supabase functions deploy reminders`. JWT checking is disabled only because these server-to-server routes validate their own secrets. Calls without the matching x-mortify-secret header are rejected.
7. Store four Vault secrets (Database > Vault, or `select vault.create_secret(value, name)`): `mortify_reminder_url` and `mortify_push_url` (the full `/functions/v1/reminders` and `/functions/v1/push-message` URLs), `mortify_reminder_secret` (= REMINDER_SECRET) and `mortify_webhook_secret` (= MESSAGE_WEBHOOK_SECRET).
8. Run `supabase/schedule.sql` in the SQL editor. It enables pg_cron and pg_net, schedules the reminder job every minute, adds a trigger that sends each new message's id to push-message, and adds public.messages to Realtime. Cron interprets each enabled user's local timezone; a delivery claim prevents duplicate reminders at the repeated daylight-saving hour, and failed sends are retried within that minute. Webhook delivery is not guaranteed; watch `net._http_response` for failures.
9. Never add the journal, falls or vault tables to Realtime.
10. Test with at least three disposable accounts: A/B same sex, C opposite sex. Verify unrelated accounts cannot select profiles/events/messages. Test accepted links, privacy toggles, parent-message validation, capacity on both sides, link removal, and sign-out while core features remain offline.

The migrations can be tested locally using `npm run test:database`. This exercises PostgreSQL semantics through PGlite; it does not replace running RLS and Realtime tests on a real Supabase test project. Cloud functions need real VAPID/SMTP configuration and device notification checks.

11. Deploy `supabase functions deploy delete-account`. Set ALLOWED_ORIGINS to comma-separated exact app origins, including the deployed HTTPS origin and native origins (`capacitor://localhost` on iOS, `https://localhost` on Android). The function validates the user's bearer token server-side, then deletes only that user's auth account; foreign-key cascades remove their cloud data.
12. Reports are kept in private.message_reports, accessible only through privileged database administration. Reporting removes and blocks the link and hides messages immediately. Establish a real owner review process and a support contact before release; the app does not promise staffed moderation or emergency response. Never expose the private schema in the Data API.
13. Report alerts: add function secrets RESEND_API_KEY (a Resend API key with send access), REPORT_ALERT_FROM (a sender on your verified Resend domain, for example `Mortify <alerts@gentleking.org>`) and optionally REPORT_ALERT_TO (defaults to mortify@gentleking.org). Deploy `supabase functions deploy report-alert`, add the Vault secret `mortify_report_url` (the full `/functions/v1/report-alert` URL), and run `supabase/schedule.sql` again. Each new report then emails the operator its id and the SQL to review it; the email never carries the message text.

Sources: [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [webhooks](https://supabase.com/docs/guides/database/webhooks), [scheduled functions](https://supabase.com/docs/guides/functions/schedule-functions), [email sign-in](https://supabase.com/docs/guides/auth/auth-email-passwordless).
